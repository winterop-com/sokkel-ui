# Rules for agents

`docs/plan.md` says what the library holds and why; `docs/roadmap.md` says what comes next;
`docs/charts.md` says how charts are drawn and which kinds there are. Read all three before starting
work.

These rules hold for every agent and every change. When a request seems to conflict with one, stop
and ask before acting.

## The library knows no app

- Never write the name of a product or app that uses this library. Only the library's own name
  may appear. That covers files, story data, comments, docs, theme and story names, scripts,
  commit messages, PR titles and bodies, and the repository's description.
- One carve-out: a domain add-on may be named for the open platform or standard it serves (`fhir`,
  `dhis2`), and that package, its stories and its docs may use the platform's own names and
  languages. An app built on that platform is still never named, there or anywhere.
- No app's domain words or data either: no app's entities, codes, hosts or vocabulary. Every
  example belongs to one fictional app, Tidevann ("tidewater"), drawn with its mark from
  `src/stories/fixtures/TidevannMark.tsx`, and uses its neutral workspace:
    - jobs such as nightly-export, sync-inventory, rebuild-index, send-digest and import-orders;
    - run states succeeded, failed, running, queued, cancelled and skipped;
    - steps fetch, transform, validate, upload and notify;
    - people ada, grace, linus and margaret;
    - the app Tidevann, with the projects harbor, juniper and larkspur;
    - services api, worker and scheduler;
    - places by plain geography: continents, countries, cities, regions, sites;
    - hosts on example.org.
- Themes are named for how they look (paper, contrast, steel), never for where they came from,
  except `tidevann`, the base theme, named for the examples app that wears it.
- Before committing, search the change for app and product names and remove every hit.

## Building components

- Apps install these packages and never copy from them. A component an app needs to differ gets an
  option here, never a local edit in the app.
- Eight packages in `packages/`: `core` (`@winterop-com/sokkel-ui`, everything without an engine
  of its own, the tokens and the themes) and two kinds of add-on on it.
    - Engine add-ons, one per engine: `charts` (ECharts: `Chart`, its kinds and the dashboard's
      chart panels), `maps` (maplibre), `graph` (React Flow and elk) and `terminal` (xterm.js:
      `Terminal` and `TerminalView`); and `media`, the music and video app parts (`MediaBar` and its
      fullscreen view, `TrackList`, `MediaCard`, `Artwork`, `useMediaSession`).
    - Domain add-ons, one per domain, each holding that domain's parts: `fhir`
      (`@winterop-com/sokkel-ui-fhir`), the health-data standards' languages, FHIRPath and CQL, for
      the code editor; and `dhis2` (`@winterop-com/sokkel-ui-dhis2`), DHIS2's expression languages
      for the code editor, UI only: it never calls a server, and takes what a server version offers
      (its function and variable names) as data from the app. A domain add-on plugs into the core as a plugin an app installs once with
      `registerPlugins` from `@winterop-com/sokkel-ui/lib/plugins`; a new kind of contribution goes
      into that module when a domain needs one, never before.
      The same lines hold for both kinds: an add-on imports the core by its name
      (`@winterop-com/sokkel-ui/...`), never by a path; the core never imports an add-on, and no add-on
      imports another. A part that needs no engine and belongs to no domain goes in the core, save the
      music and video app parts; what a core part plays through (`AudioPlayer`, `VideoPlayer`, the
      controls and `SoundVisualizer`) stays in the core. `src/rules.test.ts` holds those lines, and a new
      domain package is one more name in `DOMAIN_ADDONS` in `scripts/components-index.ts`.
- A part with a spec in `design/` (the pinned copy of sokkel-design) matches it: `src/parts.test.ts`
  checks its words, options, sizes, paints and keys. Changing what a spec covers is a sokkel-design
  PR first, then `bun run design --ref <ref>` to move the pin; `design/` is never edited by hand.
- `packages/core/tokens/tokens.json` is the only place a token is defined. Run `bun run tokens`
  after editing it; `tokens.css`, `themes.css` and the theme files in `themes/`, all under
  `packages/core/src/styles/`, are generated and never edited by hand.
- `docs/components.md` is generated by `bun run components` from the packages and the stories and
  never edited by hand; run it after adding, renaming or documenting a component.
- A new module goes in its package's `exports` map, with `types` and `import`, or in `PRIVATE` in
  `scripts/components-index.ts` with the reason it is private; `src/rules.test.ts` fails one in
  neither. A component exports the type of its props as `<Component>Props`, and a type those props
  name from a private module is exported beside it.
- Every corner derives from `--radius`. Every color, typeface and size comes from a token, so a
  theme can change it.
- A panel resizes by default, holding its own size from `defaultSize`; `size` with a size handler
  holds it from outside, and `resizable={false}` turns it off. No example holds a size only to
  turn resizing on.
- One table: DataTable draws every listing and table, short or long, flat or a tree. Its columns
  resize by default, as panels do; `resizable={false}` turns that off.
- One engine per job: ECharts draws every chart, maplibre every map, React Flow every interactive
  graph, xterm.js every terminal, hls.js every HTTP live stream, Mermaid every diagram written as
  text, KaTeX every formula, dnd-kit every drag and drop between places in a page (reorder, move,
  drop onto), and sparklines are plain SVG. A file dragged in from the desktop stays on the
  browser's own events (`use-file-drop`), and React Flow keeps its own node dragging. Never add a
  second.
- Charts are drawn with `Chart` and a kind (or `ChartGrid`, `ChartPanel` and the dashboard panels),
  never with an ECharts option built in a story. A chart the kinds cannot draw becomes a new kind or
  an option on one. `docs/charts.md` lists the kinds, the fields they read and how to add one.
- Fix the component, never the example. When a story looks or behaves wrong, the fix goes into
  the component that draws it (or a new component, or an option on one), so it reaches every
  example and every app at once. A class added to a story to patch a component's size, spacing,
  overflow or shape is a patch in the wrong place: it fixes one example and leaves the bug for the
  next. Components must hold up in any container they are given.
- An example never builds its own version of a part, layout included. When a story needs something
  no component has, the library gets the component or an option on one, and every example uses it.
  `src/rules.test.ts` fails a hand-set size or color anywhere, and in a story a selector reaching
  into a component, a raw table, a pill shape, a message under a field, or a component no story
  shows.
- Words a component says are props with English defaults, so an app can translate them.
- Words follow their context. An action or a search in a page or section drops the noun the page
  already names: on Roles the button is "New" and the field "Search", not "New role" and "Search
  roles". The noun stays where nothing around it names the thing: a dialog's title, global
  navigation and the command palette, an icon-only button's label, and an action among siblings
  that make different things ("New folder" beside "Upload files").
- Comments say what the thing does, or the constraint the code cannot show. Rationale goes in the
  commit message.
- American English everywhere: color, behavior, center. No emojis anywhere.

## Stories

- Every component has stories, including compositions with real-shaped neutral data.
- A story's name is one to three words ("Open", "Layer panel"). What it shows goes in its doc
  comment.
- The order of a file's exports is the sidebar's order: export stories from the simplest to the
  fullest (closed, short, long, then special cases), and put a new story where it belongs in that
  order rather than at the end.
- A story renders the same every time without interaction: no dates from the clock, no
  randomness, overlays opened by `open` or `defaultOpen`, and no network except the recorded map
  tiles.
- Keep the local loop light. Before a commit run only the fast gates (fmt, lint, tsc, vitest),
  and take one quick look at the main new or changed story. Never run the browser suites
  locally; CI on GitHub runs them, and its failures say which stories to look at.
- Desktop is the main target; phones, foldables and tablets must still work. A story is written
  once, at full width, and the viewport toolbar shows it at the widths layouts are checked at: 344
  and 690 for a foldable folded and open, 360, 390 and 430 for phones, 768 and 1024 for tablets,
  1280, 1440 and 1920. `e2e/layout.spec.ts` fails a story whose page scrolls sideways at any of the
  narrow ones. No story exists only to show a narrower width.
- A story uses the room the component would have in an app. One that fills its container there (a
  terminal, code, an editor, a log, a table, a schema, a graph, a chart, a video, a track list)
  fills the canvas, and the height too when it scrolls. One with a natural width (an input, a menu,
  a button, a card, a dialog) keeps that width.
- CI compares no screenshots until the looks settle near 1.0. It renders every story at the narrow
  widths and fails one that throws or whose page scrolls sideways (`e2e/layout.spec.ts`). The
  screenshot tooling stays for when it comes back: `make screenshots-ci` retakes baselines on
  GitHub into the branch `baselines` (or `baselines-for/<branch>`), and `scripts/baselines.sh`
  fetches them. Never push baselines taken on a Mac.
- Every agent shares one GitHub API limit. Wait on a run with `gh run watch <id> --interval 60
  --exit-status`, one watch per run, never a loop that polls faster. A newer push to a branch cancels the run
  of the older one.

## Examples

- `examples/<name>/{web,electron,tauri}` holds working Tidevann apps on a simulated backend
  (`examples/shared`): every page, button, menu and setting does what it says, and a dashboard
  updates live. What cannot work is left out, never stubbed.
- An example installs the packages and imports only their public entry points, as any app does. A
  part it needs that the library lacks goes into the library, never into the example.
- A library fix for a gap an example found updates that example in the same change, so it uses the
  fix, and takes the gap off the roadmap.
- Every example has Settings, and only as a `SettingsDialog` over the page it was opened from, on
  `#/settings` through the library's `useOverlayRoute` (`hooks/use-overlay-route`): never a routed
  page, never settings embedded in the layout.
- A settings dialog keeps the dialog's own footer words, and its Reset to defaults resets the shown
  section; a section with nothing to put back says `reset: false`.
- The trail lives in the top bar only, on every page; the page header shows the title and its
  actions, never a second trail.

## Design

- Show a design as a rendered story and look at the rendering before showing it. Never use ASCII
  mockups.
- When the owner is unsure, render the options side by side in one story and let the owner pick.
- A second opinion from Codex is allowed:
  `codex exec --skip-git-repo-check -s read-only "<prompt>" < /dev/null`.

## Work and git

- Work on a branch with a draft PR. Stage named paths, never everything.
- Conventional commits (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`), with no attribution lines.
- Never wait on CI. A PR is merged as soon as the fast gates pass locally; neither its own CI run nor
  main's is waited for, and a failure on main is fixed forward. A release does not wait for main's
  CI either: `release.yaml` runs the gates itself before it publishes.
- Before 1.0 a release with a breaking change moves the minor version (0.11.0 to 0.12.0); one
  without moves the patch.
- No tags and no releases unless the owner asks for one. A release is a PR that moves the version
  in every `packages/*/package.json` to the same one; once it is merged, the tag `vX.Y.Z` on that
  commit runs `.github/workflows/release.yaml`, which checks the tag against each package's version,
  runs the gates, builds, and publishes every package to GitHub Packages. Then a GitHub release
  with the notes.
- Ask before any outward or hard-to-undo action: publishing, changing repository settings,
  rewriting history, force-pushing, deleting.
- Agents working in parallel each write scratch files in a folder of their own, and never touch
  another agent's files.
